# Changelog

## 2.2.6 — 2026-10-10

- **Built-in engine updated to Drakmor's fpkg-gui 0.6.11** (`libs/LibProsperoPkg.dll`; `libScePubTools.dll` unchanged). Fixes that come with the engine itself: NAPS errors, the DLC (additional content) build process, files containing `00000000000000000000000000000000` being dropped from the package because they were mistaken for a passcode, and automatic generation of `sce_sys/about/right.sprx`. Progress parsing was checked against the new engine's log lines — the formats are unchanged.
- **PlayGo: the source layout is kept (thanks to @MangoScango).** When `sce_sys` still has `playgo-chunk.dat`, `playgo-ficm.dat` and `playgo-hash-table.dat`, the engine puts every file back into its original chunk with the original chunk labels and languages, and rebuilds the physical ranges for the new image. Voice languages are organized correctly and can be removed from the game's add-on content menu. The chunk count is detected from the table automatically.
  - **Default changed: `sce_sys/playgo*` files are now kept** (*Drop every sce_sys/playgo* file* is off). Settings saved by earlier versions are migrated once, since they stored the old default. Broken PlayGo files are still dropped, and if the source tables cannot be used at all the build switches to a generated layout with a warning instead of failing after compression.
  - New **PlayGo layout** option (built-in engine): *Source layout (automatic)* or *Generate for languages*, with a list of the 31 PlayGo languages to choose from. CLI: `--playgo-languages ja-JP,en-US` (or `all`), `--remove-playgo`; `--keep-playgo` is accepted and is now the default.
  - The build log states which layout is used (chunks, scenarios, languages). A dump without `playgo-chunk.dat` gets a hint: the tables can be extracted from the game's `_sc` package with prosperopatches and copied into `sce_sys`.
- **Choose how many CPU cores the Sony SDK uses — and change it while it builds** ([#6](https://github.com/thanhsondev/PSVIETHOA-FPKG-Builder/issues/6)). The *Compression threads* box was locked at 0 in SDK mode, because Publishing Tools has no thread option: it reads the core count from Windows (`GetSystemInfo`) and starts a worker for every core (measured under Wine: ~1370 % CPU on 15 cores). The box now shows the machine's core count by default (full speed, stored as "every core") and can be lowered. A new **CPU cores** box next to the Build/Cancel button changes it **during** a build, so you can free the computer while you work and give it back afterwards. How it is limited (`CpuLimiter`): Windows sets the CPU affinity of `img_create`; macOS and Linux throttle it like `cpulimit` — the process is paused (SIGSTOP/SIGCONT) whenever it has used more than N cores' worth of CPU in the last 100 ms. Measured with the real toolchain on macOS: limited to 4 of 15 cores, `img_create` averaged ~4.2 cores and the package was built and verified normally. The package is unchanged. CLI `--threads` now applies in SDK mode as well.
- **The window is never cut off, on every OS.** On a Retina Mac the opening size was computed by dividing the screen's working area (reported in points) by the render scale a second time, so it only fit because the 1080 px minimum width masked it; the conversion now uses the screen's own scale on macOS, Windows and Linux, the window is re-centred inside the working area, and the minimum drops to the screen size on small displays (MacBook 13", 1366×768 laptops). The header no longer pushes the theme and Help buttons off the right edge: the tagline and credits shorten with "…", the debug-keys chip becomes an icon below 1240 px, and the version badge and the Help label give way near the 960 px minimum. The status bar trims the credits instead of the version, and the two-column Build and Extract layouts scale between 420–600 px and ≥ 360 px instead of a fixed 580 px left column. The Help window fits the screen the same way.
- **Number boxes redesigned**: the value is vertically centred and the oversized ▲▼ buttons are replaced by two small stacked arrows that dim at the limit. `Styles/ControlThemes.axaml` was never loaded by the app, so its themes are now active as designed — the mode bar and the VI/EN switch show the segmented style instead of plain radio buttons.
- Fixed: the settings file always stored PlayGo defaults revision 1, so every launch re-ran the 2.2.1 migration and switched *Clear attribute3* back off.
- The Extract tab already supported choosing individual files and already exports every `sce_sys` file (PlayGo tables included), so the engine's new selective-unpacking API is not needed there.

## 2.2.5 — 2026-09-25

- **Sony SDK mode now uses the `sdk-fpkg279-fix12` toolkit** (profile unchanged: `sdk279-plaintext-direct-v3`). `libs/sony-sdk` is replaced as a whole — patched `prospero-pub-cmd.exe` / `libScePubTools.dll`, `prospero-dds2png.exe`, `create-gp5-from-folder.py` and the launchers — and the app reproduces the new script byte for byte (`SonySdkFidelityTests` runs the script itself with `--chunk-count 100/2/1 --auto-size-profile sdk279`, the flags `build-from-folder.ps1` passes, and compares the GP5, scenario, `param.json`, converted PNGs, repaired SELFs and the `01-create-gp5.log` text). What fix12 changes:
  - **Up to 500,000 files** in a large (lv2) package with the patched Publishing Tools.
  - **PlayGo chunk count 1–255** (default 100). The existing *PlayGo chunks* box now applies to Sony SDK builds down to 1 chunk; when there are fewer chunks than voice languages, the remaining languages share the last chunk instead of the build failing.
  - **Automatic package size.** For a full package the normalized `param.json` gets the smallest `attributePub` (0 / lv1 / lv2) that fits the uncompressed size of the files actually mapped into the GP5 plus a metadata allowance, and `kernel.addcontMountLevel` is lowered only as far as needed (2 → 1 or 0, 1 → 0) with a warning. The source file is untouched. Update packages keep the source `attributePub`, as in the toolkit. Requires a native game (`applicationCategoryType: 0`).
  - **Image conversion fixes.** Every `sce_sys/*.dds` is considered, not only `pic*`: a PNG that is missing **or in the wrong colour mode** (icon0/pic0/pic1 must be 8-bit RGB, pic2 8-bit RGBA) is rebuilt from its DDS into `.gp5-assets`; a wrong-mode presentation PNG without a DDS stops the build with a clear message instead of failing inside `img_create`.
  - **SELF header repair.** SELF files with the PS4 magic or a misaligned `.sceversion` trailer are rewritten into `.gp5-assets/<name>/normalized-self/`; the source is never modified.
  - More SDK-generated inputs are excluded: `sce_sys/pfs-region-hints.json`, `origin-/target-relocinfo.dat`, and the reserved root folders `sce_suppl/` and `sce_sc/`.
  - The toolkit's notes also list a fix for skipping `about/right.sprx`. The script still leaves `sce_sys/about/` for Publishing Tools to regenerate, so the app keeps doing the same; any change is inside the patched binaries.
- **New option (on by default): *Clean up dump leftovers*.** Leaves the root `_DUBLEX_` folder, Unreal Engine's `Engine/Saved` (the whole `Engine` folder when `Saved` is all it holds) and `<project>/Saved` (Stellar Blade: `SB/Saved`) out of the package. These leftovers cause a hard splash lock (a hard reset is needed) in **Stellar Blade (DLPS, PPSA13197 EUR with DLC)**; with them removed, together with the existing AMPR cleanup (`ampr_emu.index`, `fakelib/libSceAmpr.sprx`), the game, DLC and languages work. **Credit: the cleanup method was shared by the community.** Works for folders, extracted `.ffpkg`/`.exfat` images and Dokan mounts; nothing in the source is deleted. CLI: `--keep-dump-leftovers`.

## 2.2.4 — 2026-09-21

- **A base package built by the built-in engine is rejected in 0.3 s instead of after the whole package has been compressed, and 2.2.3's explanation of this error is corrected.** Reported case: an update build against a 33 GB Days Gone: Remastered base package stopped at 94 % with `Unexpected logical error. (NAPS metadata missing)` after 4 min 1 s. 2.2.3 assumed the cause was a repacked base package whose supplement region had been stripped, and only checked that the region exists (`PackageInfo.HasSupplement`, i.e. `SupplementSize > 0`). **That assumption was wrong.** Measured on the reported package: the supplement region is present (47.5 MB), holds `common/etc/naps_meta_18.dat` (45.3 MB), and that file decrypts cleanly with `ProsperoNapsMeta.DecryptMeta18` into a well-formed TLV stream (`phdr`, 1 × 24 bytes, then `file`) whose block count matches the package header exactly. Nothing is missing.

  The real cause is *who wrote it*. Building the same source twice — once through the Sony SDK, once through the built-in engine — gives two different supplement regions:

  | | Sony SDK (Publishing Tools) | Built-in engine (LibProsperoPkg) | Reported base package |
  |---|---|---|---|
  | `naps_meta_18.dat` decrypts with the library key | no (own key) | **yes** | **yes** |
  | `naps_meta_300/301/302/308.dat` | 72 bytes (3 × 24-byte records) | **48 bytes (2 records, no `id=1`)** | **48 bytes** |
  | SI members | 8 (incl. `playgo-scenario.json`) | **7** | **7** |

  So the base package was built by the built-in engine. `img_create --ref_pkg_path` reads `prev_suppl/common/etc/naps_meta_18.dat` (the string is in `libScePubTools.dll`) and decrypts it with Publishing Tools' own key; against a built-in-engine package that yields garbage, and the toolkit reports the metadata as missing — but only after compressing everything.

  New `SonySdkReferenceProbe` tells the two producers apart by reading that one ZIP member (`ProsperoPublishingSidecar.TryReadNapsMeta18`, nothing written to disk) and testing whether it decrypts into a `phdr` TLV. `SonySdkPatchReference.Inspect` now stops on a built-in-engine base with a message that says which engine made it and what to do (rebuild the base with Sony SDK on, or leave the base package box empty and build a full package). Measured on the reported package: **0.31 s, versus 4 min 1 s before**; on a 100 GB game the old path costs hours. A package with no supplement region at all keeps the earlier message, reworded — the "repacked by an external tool" wording was part of the wrong diagnosis and is gone.

  Tests build a base package with each engine through the real toolchain and assert the fingerprints, that the built-in-engine base is refused before any `SDK:` log line or output file appears, and that the Sony SDK base built from the same source still produces a patch.

## 2.2.3 — 2026-09-20

- **A base package without NAPS metadata is rejected before the build instead of after it.** `img_create --ref_pkg_path` reads the base package's supplement region for `common/etc/naps_meta_*.dat` (`prev_suppl/common/etc/naps_meta_18.dat` in `libScePubTools.dll`); a package that was repacked by an external tool — a `P30Day`/license-patched or re-shared build — can be missing it, and Publishing Tools then stops with `Unexpected logical error. (NAPS metadata missing)` **only after compressing the whole package** (reported: 3 min 56 s for a 3 GB game; hours for a 100 GB one). `SonySdkPatchReference.Inspect` now checks the supplement region, which it already reads from the header, and stops in a second with a message that names the cause and the two ways out (use a base package built by this tool, or leave the field empty to build a full package). Verified against six real packages — Ghost of Yōtei, GTA V, Stellar Blade + DLC, FFVII Rebirth and a third-party DUPLEX unlocker — all of which carry the metadata and are accepted. The base package from the original report was not available, so the deeper case (supplement present but `naps_meta` missing inside) is not covered: checking that needs the SI entries extracted (measured: 2.2 s and 103 MB of temporary files for a 96 GB package), which is too much for every build. `fpkg-cli pkg-extract <pkg> --cnt` writes the SI entries when a specific package has to be diagnosed.
- **Games that use `sce::Ampr` are flagged before compression starts, not after.** `AmprInspector` was only used by `inspect` and when a source was opened, where it printed one Info line among many; the build itself said nothing. `BuildEngine` now warns at the point every path passes through (Sony SDK, SDK + Dokan mount, update patch, built-in engine), so the warning arrives before the wait rather than after it. The message is explicit that this is **not** a sign of a patched executable: `libSceAmpr` is a real PS5 library (AMM + APR) and the game's own `eboot.bin` imports it. Checked on the dumps that keep an `eboot.bin.esbak` backup next to `eboot.bin` (Ghost of Tsushima, PPSA08772, FATAL FRAME II, Monster Hunter Wilds, Resident Evil 7, Alan Wake Remastered): the backup always has the same AMPR status as the executable beside it, so restoring it changes nothing. Packages of such games can hang on the splash screen; the remedy is to run the game as a folder instead.
- Drive audit of 54 game dumps on two exFAT drives in `docs/research/drive-audit-FG.md` (+ `game-survey-F/G.json`): every dump has `sce_sys`, `eboot.bin`, `icon0.png` and a 96-byte keystone and passes `fpkg-cli inspect`; 14 games use AMPR, 6 carry a DLC emulator, 8 have `#`/`[`/`'`/`,` in file names (GP5 generation verified on the worst of them — 40 820 files with `#`), 2 folder names end in a hidden U+F028 character, and 239 997 of the 813 556 files are macOS junk (`._*`, `.DS_Store`, `*.url`) that the builder already leaves out of every package on both source paths.

## 2.2.2 — 2026-09-19

- **New tab: *Build Update PKG* — like Patch Builder on PS4, built the Sony SDK way.** A PS5 update is not a PS4-style overlay package: Publishing Tools 2.79 has no patch volume type (`prospero_app` / `prospero_ac` / `prospero_al` only); an update is a `prospero_app` with a higher `contentVersion` built with `img_create --ref_pkg_path <base.pkg>`, which writes a block-level delta tied to exactly that base package (digest link). The tab does that with three choices:
  The input is always the base `.pkg` (the one installed on the console) plus the source — the full new game **or just an update folder** with the files you changed or added (`eboot.bin`, `sce_sys`, `fakelib`, translation files…). The app compares file paths with the base package's file list: files in the source are used as they are (*replaced* — keeping the base package's exact name/case — or *added*), every file the source does not have is taken from the base: from the optional *Original game folder* (read only, nothing extracted) or, when that is empty, by extracting just those files from the base package into the temporary folder (free space checked, removed afterwards). Measured: a project that lists only the changed files produces a new version with everything else deleted, which is why the unchanged files must be readable. Choose what to keep:
  - **Update file only** — `UPDATE_….pkg`, the small package to install over the base;
  - **Full game with the update** — `….remastered.pkg`, the whole game at the new version (base + update in one file);
  - **Both**.

  Publishing Tools always writes both; the file that was not chosen is removed after the structure check (the two convert into each other with `img_convert`, so nothing is lost).

  Outputs: `UPDATE_<contentId>-A…-V….pkg` (the small package to install over the base) and `<contentId>-A…-V….remastered.pkg` (the full new version Publishing Tools writes next to it, for checking/extracting). The "output folder already has a package" question never offers the base package for overwrite. A folder without `sce_sys` is fine: Content ID comes from the base and the version is pre-filled one step above it (*Raise the content version to …*). The log and `01-create-gp5.log` list every replaced (`*`) and added (`+`) file; a source that changes nothing stops the build. The patch block left the *Build PKG* tab. CLI: `--sdk-reference <base.pkg>` (+ optional `--sdk-base-folder <dir>`), `--sdk-patch-output update|full|both`, `--sdk-base-folder <dir> --sdk-build-base` to build the base package from the original game folder first and the update against it, `--sdk-patch-exact` to treat the source as the complete new version (missing files = deleted, like the toolkit).
- **Content version and App title are now applied to Sony SDK packages.** The two fields in step 2 are written into the package's `param.json` (`contentVersion`, `titleName` of the default language) when they differ from the source — the source is never touched, and leaving them as read keeps the package byte-identical. The patch check now compares the *Content version field* with the base package, so "contentVersion must be higher" is fixed by typing a higher number (or the new *Raise the content version to …* link) instead of hand-editing `param.json`. CLI: `--version` / `--title` do the same; the queue keeps each source's own values.
- **DLC packages from `dlc_emu.ini`: every `[PSAC]` entry is built** (it used to stop with "Built 0/N" when the entries were not `NO_EXTRA_DATA`). Entries without extra data give an unlock-only package as before; entries with a `mount_point` whose folder exists in the game (`/app0/dlc01` → `<game>/dlc01`) are packed with that data (the game folder is only read); entries with data that cannot be found still give an unlock package plus a warning. `[PSAL]`/`[PSCONS]` sections are skipped with a note.
- **Fixed a possible crash when several builds start at the same time on macOS** (queue): .NET's drive enumeration (`getmntinfo`) is not thread-safe and could take the whole app down with an access violation; drive lookups are now serialised.
- **Update patches (toolkit `sdk-fpkg279-fix8-deltas`).** New optional block in step 1, *Build a patch against an installed base package*: pick the `.pkg` that is installed on the console and Publishing Tools compares the new build with it (`img_create --ref_pkg_path`) and writes only the differences — `<name>.pkg` is the small update to install over the base package, `<name>.pkg.remastered.pkg` is the full companion used for checking/extracting. The app reads the base package as soon as it is chosen and shows its Content ID / version under the field; a different game, or a `contentVersion` that was not raised in `param.json`, is reported right there and stops the build before Publishing Tools runs (the SDK would only fail after compressing everything). The structure check runs on the companion (a delta has no FIH header); the log reminds the install order. Sony SDK only — with the built-in engine, or when the SDK is unavailable, the build stops instead of silently producing a full package. CLI: `--sdk-reference <base.pkg>`. The queue always builds full packages. Bundled toolkit files updated to fix8 (`ric.exe`, `prospero-dds2png.exe`, scripts; `prospero-pub-cmd.exe` is unchanged from fix6). Measured: a 1 KB change in a 7 MB game gives a 1.5 MB patch.
- **More tests for every platform** (323 in total): localisation key/placeholder parity between Vietnamese and English and format-string validity, the bundled toolkit's file list, OS-dependent services never throwing where they do not apply (sleep guard, component probe, Rosetta/VC++/Wine lookups, update asset names), alias folders never on the source drive, output names valid on every file system, plus the patch flow through the real SDK (delta + companion, version not raised, base package of another game, no SDK).
- **Toolkit updated to `sdk-fpkg279-fix6` (profile `sdk279-plaintext-direct-v3`).** The patched `prospero-pub-cmd.exe` now writes the PLAINTEXT_NOAUTH package directly, so the third step (the post-process conversion) is gone: the package is written as `<name>.partial.pkg` and renamed. The C# converter stays as a fallback for packages that come out without the plaintext marker (older toolkits).
- **PlayGo for dumps without `playgo-chunk.dat`, the way the new toolkit script does it**: 100 chunks, game files in chunk 0, and **one chunk per language** listed in the dump's `playgo-scenario.json` (or derived from its localisations), each holding a 1 MiB uncompressed placeholder (`playgo-languages/NN-<lang>.bin`) so the console reports every voice language as installed; the source scenarios, titles and default scenario are kept, every chunk is initial. The GP5, scenario file and `param.json` are byte-identical to the script's output (checked against the bundled Python script on a two-scenario, three-language fixture). An invalid scenario file falls back to the default scenario with a warning instead of stopping. Dumps that still have the original tables (Ghost of Yōtei) keep their real chunk layout and file map as before — the script cannot do that.
- **Like the toolkit, the generated `.gp5`, `.playgo-scenario.json` and `.gp5-assets` are removed after a successful build**; the `-build-logs` folder stays. New option *Keep the GP5 and generated files* / `--sdk-keep-intermediate`.
- **Windows: Publishing Tools' own temporary files go to the app's temporary folder** (TEMP/TMP of the SDK process), so they follow the drive chosen in the app instead of always landing on C:.
- **macOS 27: Rosetta 2 is detected correctly and can be reinstalled from the app.** A major macOS upgrade (macOS 27) removes Rosetta 2 and leaves only `RosettaLinux` in the `oah` folder; the old check took that for an installed Rosetta and Wine then died with "Bad CPU type in executable". The app now requires `libRosettaRuntime`, explains what happened, and the Sony SDK warning has an **Install Rosetta 2** button that runs Apple's `softwareupdate --install-rosetta --agree-to-license` after a confirmation (no admin password), then re-checks the components. Verified on macOS 27.0: the whole suite including the real Publishing Tools builds passes, The Smurfs – Dreams (9.5 GB) builds in 32 s.
- **Build queue — several games at once.** A third mode next to *Build PKG* / *Extract PKG*: drop game folders, disk images or a whole dump drive into the queue (a folder that is not a game itself adds every valid sub-folder), choose how many builds run in parallel (1–4, default 2), press Start. Each entry has its own progress bar, phase, ETA, elapsed time, result path and log (select an entry to read its log); entries can be re-ordered, cancelled, retried or removed individually, the whole queue can be paused (running builds finish, nothing new starts) or cancelled, and finished entries cleared. Each build uses the Build PKG tab's settings at the moment it starts (Sony SDK, DRM, compression level…) and the "Auto from source" output rule; a package with the same name in the output folder is renamed and kept instead of asking. Two entries with the same Content ID into the same output folder never run at the same time (the second is skipped with a note). The window asks before closing while the queue is building.
- **Fixed: "reserved node found (dst_path sce_sys/origin-param.json / target-param.json)" when rebuilding a folder that Extract PKG produced.** Publishing Tools keeps the original and target `param.json` of a patch/backport as `origin-param.json` / `target-param.json` inside the package's CNT, Extract PKG writes them back into `sce_sys/`, and the SDK rejects both names in a GP5 (measured; `nptitle.dat`, `npbind.dat`, `pubtoolinfo.dat`, `changeinfo/`, `*-deltainfo.dat` are accepted). Both files are now skipped like `license.dat`; the toolkit's own script lacks these entries.
- **Fixed: "Format of the png file is not valid (sce_sys/pic2.png)" on folders produced by Extract PKG.** Some packages carry a few hundred bytes of junk under the name `pic2.png` in their CNT; Extract PKG writes it back and Publishing Tools then refuses the whole build. A splash/icon PNG that is not a valid PNG (signature, IHDR, 8-bit RGB/RGBA, non-interlaced) is now left out of the GP5 and rebuilt from the `.dds` copy with prospero-dds2png, exactly like a missing PNG (the log says which file was replaced).
- **Faster "creating the GP5 project" when splash PNGs must be rebuilt from DDS.** The prospero-dds2png conversions now run in parallel (one process each, up to half the CPU cores) instead of one after another; on macOS every 4K BC7 image cost ~5 s through Wine, so a game missing nine `pic2_XX.png` files spent 50 s of a 2-minute build there (The Smurfs – Dreams, 9.5 GB, measured).
- **Parallel builds are isolated**: the Wine prefix is created once even when several SDK builds start together, cancelling one SDK build no longer kills the `wineserver` shared with the others, and every build keeps its own temporary, mirror and ASCII-alias folders. Tests: two SDK builds in parallel, and cancelling one while the other finishes.

## 2.2.1 — 2026-09-18

- **Fixed: "Something went wrong (CE-108111-2)" dialog when launching a game rebuilt with its original PlayGo chunks (Ghost of Yōtei).** The original tables mark only the first 32 of 35 chunks as initial (the rest stream in later on a retail install), so the game asked the system about the "later" chunks at start-up and the system answered with that dialog (the game then continued normally). Every scenario now marks all of its chunks as initial — an FPKG is fully installed, nothing arrives later — while chunk order and per-chunk languages stay as in the original package. LibProsperoPkg 0.6.9 does the same.
- **Engine updated to fpkg-gui 0.6.9** (LibProsperoPkg.dll): language chunks generated from `playgo-scenario.json`, improved PlayGo validation.
- **PS5 Pro Enhanced / 120 Hz / VRR are kept.** "Clear the attribute3 flags in param.json" is now **off by default** (CLI: `--clear-attribute3` to opt in; `--keep-attribute3` still accepted). `attribute3` is the game's feature-flag field — bit 7 = 120 Hz, bit 19 = VRR, bit 23 = PS5 Pro Enhanced (a game supporting all three stores 4456512) — so the old default of zeroing it made PS5 Pro consoles run such games without their Pro enhancements. The zeroing came from an old "uncheck the PlayGo flags" black-screen guide; no public documentation maps any PlayGo bit in attribute3, the real PlayGo problem is solved in the PlayGo tables since 2.1.7/2.2.0, and Sony's own toolkit leaves the field alone. Existing settings are migrated once (`PlayGoDefaultsRevision` 2); the option and the plan log still explain what the bits mean.
- Verified against Publishing Tools: with the option off, `attribute3` (e.g. 4456512) survives the SDK build unchanged in the package's `param.json`. Note on `sce_sys/about/right.sprx`: Publishing Tools rejects the whole `sce_sys/about` directory as a reserved node and does not regenerate it, so SDK-built packages have no `right.sprx` — that module only provides the logo/copyright screen (▲+■+Options on the game's Information page) and has nothing to do with PS5 Pro; the built-in engine keeps it as before.

## 2.2.0 — 2026-09-18

### Verified on the Windows research pass (2026-09-17/18)

- **Ghost of Yōtei voice fix confirmed at the package level.** The dump's original PlayGo table has 35 chunks (29 per-language `pgc_lang_*` chunks, several sharing the same language mask), 1 scenario with `initial_chunk_count = 32`; the game's `eboot.bin` imports `libScePlayGo`. Publishing Tools 2.79 accepts the GP5 written by the app, and a package built from a fixture carrying the real tables reports an identical structure (chunks, masks, labels, scenario, initial count, default language, every file in the same chunk). A synthetic 35-chunk test with duplicate masks now runs through the real SDK. PS5 confirmation still pending.
- **playgo-scenario.json of the original package is reused** for multi-chunk sources when it matches the scenario structure: Publishing Tools copies this file into the package verbatim, and the PlayGo tables do not depend on it.
- **Byte-for-byte fidelity with the toolkit on Windows.** The toolkit's Python script writes the `.gp5`, `.playgo-scenario.json` and the normalized `param.json` with CRLF line endings (text mode on Windows); the app wrote LF, so the scenario file inside the package differed (15 bytes). The app now writes CRLF on every platform. Verified: the same fixture built by the original `build.bat` and by the app gives packages of identical size whose only differing bytes are build timestamps and the digests that depend on them.
- **Much faster SDK builds on Windows: parallel pre-scan.** Windows Defender scans every file on its first open (~11 ms), and `img_create`'s "Checking files to see if compression/conversion is needed" opens files one by one — Ghost of Yōtei (95,386 files) spent about 25 minutes there. The app now opens every source file read-only in parallel before running Publishing Tools (~700 files/s instead of ~90 on this machine), so the SDK's check finds the scan results cached (2,011 fresh files: 22.5 s → 0.4 s). Nothing is written; the GP5 and package are unchanged. On by default; CLI `--no-sdk-prescan`, GUI toggle under Sony SDK options.
- **New opt-in Sony SDK options** (defaults stay identical to the toolkit): compression level for `img_create --compression_level` (-4..9, CLI `--sdk-compression-level`), and **PlayGo fallback** for sources whose dump no longer has `playgo-chunk.dat` (24 of 25 dumps surveyed) — N chunks (`--playgo`, default 100) and the scenario count of the source's `playgo-scenario.json` (The Last of Us Part I/II keep 2 scenarios), like the built-in engine, instead of 1 chunk / 1 scenario (CLI `--sdk-playgo-fallback`).
- **Clear error for file names Publishing Tools rejects.** Measured with `img_create`: every printable ASCII character is accepted except `%` and `;`; any non-ASCII character and names ending with a dot are rejected ("invalid attribute value dst_path"). ## 2.1.0 — 2026-09-13

Updated to the latest **LibProsperoPkg** (from `fpkg-gui 0.6.2`) and exposed its new capabilities.

### Library (LibProsperoPkg)
- Faster large-package builds through overlapping reads, compression and writes, with fewer intermediate copies.
- Block deduplication and an in-build compression cache.
- Improved built-in Kraken compression, especially at levels 8–9.
- PFS v2 / v3 selection, configurable compression block size and automatic shuffle selection for PFS v3.
- Automatic fallback to the built-in Kraken encoder when Oodle Reduced is unavailable.
- Improved progress reporting (byte throughput), reduced log verbosity.
- File-handling and build-cancellation fixes; existing packages are preserved if a rebuild fails.

### Measured on a 21.3 GB real game (macOS, Apple Silicon, built-in Kraken)
| Library | Time | Package |
|---|---|---|
| LibProsperoPkg shipped with 2.0.0, "Kraken 7" (= Normal encoder) | 3 min 40 s | 9.03 GiB |
| LibProsperoPkg shipped with 2.1.0, **Standard (Kraken 4, default)** | **2 min 13 s** | **8.86 GiB** (−1.9 %) |
| LibProsperoPkg shipped with 2.1.0, Smallest (Kraken 7 Optimal) | 12 min 49 s | 8.54 GiB (−5.5 %) |

Side by side on the same 400 MB set the 2.0.0 engine produced identical packages at levels 4 and 7 (its "level 7" was the Normal encoder) and the 2.1.0 engine at level 4 reproduces that result at the same speed, so **Standard** keeps the old size and speed while **Smallest** is a genuinely new, slower Optimal mode.

### App / CLI
- New advanced options: **PFS compression format (v2 / v3)**, **Kraken block size (128–256 KiB)**, **pre-compression shuffle pattern**, **automatic shuffle analysis**, **skip PFS input check** (expert), **physical layout optimisation**.
- **Presets re-mapped to the new encoder.** The 2.0.0 engine used the same Normal encoder for levels 4–7 (identical output at level 4 and 7); in 2.1.0 level 4 reproduces that result at the same speed while level 7 is a new, ~5–6× slower *Optimal* mode. The default preset is therefore **Standard = Kraken 4** (the old "Kraken 7" size and speed, plus dedup/layout gains; CLI id `balanced`, aliases `sony` / `standard`); **Smallest = Kraken 7 Optimal** (~3 % smaller, 5–6× slower) stays available.
- New **Maximum** preset (Kraken 9 + PFS v3 + shuffle analysis) next to Fast / Standard / Smallest. Per the library author: the PFS v3 shuffle mechanism optimises texture compression, is very time-consuming and only fully effective at level 9, and PFS v3 packages need PS5 firmware 7.00 or newer — the app shows these warnings in the advanced options and the build log.
- Build panel shows the live **throughput** (MiB/s) next to the ETA; progress model covers the new planning and layout phases.
- Smoother progress on large games: the inner-compression phase is now estimated from the library’s per-file lines (byte-weighted), so the bar moves every few seconds instead of once per multi-GB file; phase weights re-tuned from a 21 GB real-game build.
- New `PSVIETHOA_SCROLL=<pixels>` dev hook for documentation screenshots.
- CLI: `--pfs`, `--block-size`, `--shuffle`, `--shuffle-analysis`, `--shuffle-prediction-level`, `--skip-pfs-input-check`, `--no-layout-optimization`, `--source-mode`, `--project` (GP5).
- New **Extract PKG** mode (Build | Extract mode bar under the header): inspect a `.pkg` (FIH / CNT headers, region map, every `param.json` field, icon, sce_sys entries) and list the files of the inner PPR-PFS image; filter, tick files/folders and extract a selection or the whole package with progress and cancel; export `sce_sys` / SI entries; optional SHA-256. PLAINTEXT_NOAUTH packages are decoded in place in 4 MiB chunks (LRU cache, no temp image); Native (AES-XTS) packages are decrypted to the temp folder first; retail packages are information-only. CLI: `pkg-info`, `pkg-list`, `pkg-extract` (`--include` globs, `--cnt`, `--threads`). Dev hooks `PSVIETHOA_MODE=extract`, `PSVIETHOA_EXTRACT_PKG=<pkg>`, `PSVIETHOA_EXTRACT_PREVIEW=<path or file name inside the package>`, `PSVIETHOA_AUTOEXTRACT=1`.
- **GP5 project as a third source type** (`.gp5`, mirroring fpkg-gui's Folder | GP5 selector): ".gp5 project" button in step 1 and drag & drop; metadata, size and validation are read through the project (Normal or Flat layout, `global_exclude` / `dir_exclude` / `file_exclude` masks, relative paths resolved from the `.gp5` folder); the project's passcode pre-fills the passcode field; new advanced **Source reading mode** (automatic top-level `.gp5` / folder only) for folder sources; `fpkg-cli inspect` and `build --source x.gp5`.
- New PSVIETHOA logo (`docs/logo.svg`): app icon on macOS / Windows, window header and README banner are generated from it (`scripts/make-icons.py`, `scripts/make-banner.py`).
- Credits shown in the header, footer, help window and CLI.
- Fixed: runtime language switch now updates every label; help window no longer overflows horizontally.
